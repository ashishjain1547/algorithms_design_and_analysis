Dynamic Programming, Explained with the Simplest Example: Climbing Stairs

Dynamic Programming (DP) is one of those topics in programming that can initially sound much more complicated than it actually is.

The name itself can make it feel mathematical or advanced. You may hear words such as state, transition, recurrence, memoization, and tabulation and wonder whether you need to understand all of that before solving your first DP problem.

You do not.

A much better way to learn DP is to start with a problem so simple that the underlying idea becomes almost impossible to miss. The classic Climbing Stairs problem is perfect for that.

In this post, we start with the problem itself, solve it in the most natural way, notice the repeated work, and then gradually turn that observation into a dynamic programming solution. We also look at an implementation that uses only two variables instead of a DP array.

The goal is not merely to memorize a solution. The goal is to understand why this is DP and how to recognize the same pattern when a different problem appears in an interview or coding exercise.

1. The Problem: Climbing Stairs

Imagine that you are standing at the bottom of a staircase.

The staircase has n steps.

You are allowed to climb either:

  • 1 step at a time, or
  • 2 steps at a time.

The question is:

How many different ways can you reach the top?

Let's start with a very small staircase so that we can solve it by hand.

If there is only 1 step

There is only one possible way:

1

So there is 1 way to reach the top.

If there are 2 steps

There are two possibilities:

1 + 1 2

So there are 2 ways.

If there are 3 steps

Now things become slightly more interesting:

1 + 1 + 1 1 + 2 2 + 1

There are 3 ways.

If there are 4 steps

We can list all possibilities:

1 + 1 + 1 + 1 1 + 1 + 2 1 + 2 + 1 2 + 1 + 1 2 + 2

There are 5 ways.

So we already have a small sequence:

Number of steps Number of ways
11
22
33
45
58
613

Something familiar may already be visible here. This is the Fibonacci-like pattern where each value is obtained by adding the previous two values.

But rather than jumping straight to a formula, let's understand why that happens.

2. The Key Question: What Could the Last Step Have Been?

Suppose we want to reach step n.

We are allowed to move either 1 or 2 steps at a time. Therefore, the final move must have been one of only two possibilities.

Possibility 1: We came from step n - 1 by taking one step.
Possibility 2: We came from step n - 2 by taking two steps.

There is no third possibility.

So, if we know how many ways there are to reach step n - 1 and how many ways there are to reach step n - 2, we can calculate the number of ways to reach step n.

ways(n) = ways(n - 1) + ways(n - 2)

This tiny equation is the heart of the problem.

Notice what we have done. Instead of trying to list every possible sequence of jumps to reach step n, we reduce the problem to two smaller versions of the same problem.

That is the first major idea behind dynamic programming.

Big problem: How many ways can I reach step n?

Smaller problems: How many ways can I reach step n - 1 and step n - 2?

Combine them: Add those two answers.

3. Why the Formula Works, Without Guessing It

Now let's address the deepest confusion directly.

Why do we not need to count the final 1-step and 2-step moves separately?

Because the recurrence already includes them in the structure of the problem.

If the last move was 1 step, then the path must end with:

... → n - 1 → n

There are ways(n - 1) ways to reach n - 1, and from each such path there is exactly one valid final move: take 1 step to reach n.

Similarly, if the last move was 2 steps, then the path must end with:

... → n - 2 → n

There are ways(n - 2) ways to reach n - 2, and from each such path there is exactly one valid final move: take 2 steps to reach n.

So the contributions are simply:

ways(n - 1) + ways(n - 2)

No extra multiplication is necessary because every complete path to the smaller state has exactly one way to finish the final move.

The final move is already accounted for by the fact that every path reaching n - 1 or n - 2 can be extended by exactly one corresponding move.

4. Let's See It Clearly with n = 4

All ways to reach step 4 are:

1 + 1 + 1 + 1 1 + 1 + 2 1 + 2 + 1 2 + 1 + 1 2 + 2

Now look only at their last move.

Ways ending in 1

1 + 1 + 1 + 1 1 + 2 + 1 2 + 1 + 1

If we remove the last 1 from each, we get:

1 + 1 + 1 1 + 2 2 + 1

These are exactly the 3 ways to reach step 3.

So the number of ways ending in 1 is ways(3).

Ways ending in 2

1 + 1 + 2 2 + 2

If we remove the final 2, we get:

1 + 1 2

These are exactly the 2 ways to reach step 2.

So the number of ways ending in 2 is ways(2).

Combine them:

ways(4) = ways(3) + ways(2) = 3 + 2 = 5

5. Why Are We Allowed to Add Them?

Every path to step n must end with exactly one last move.

That final move must be either:

  • +1, or
  • +2.

A path cannot end with both. So the two groups are completely separate.

This is the real reason behind the recurrence: we divide all possible solutions into two mutually exclusive groups depending on their last move.

6. The Recurrence Emerges Naturally

All ways to reach n can be divided into:

  1. Ways whose last move is 1 step.
  2. Ways whose last move is 2 steps.

The first group has ways(n - 1) possibilities.

The second group has ways(n - 2) possibilities.

Therefore:

ways(n) = ways(n - 1) + ways(n - 2)

Notice that we did not memorize this formula. We derived it from the structure of the problem.

7. Base Cases

To use the recurrence, we need to know where it starts.

One step

There is only one way:

1

So:

ways(1) = 1

Two steps

There are two possibilities:

1 + 1 2

Therefore:

ways(2) = 2

Now the sequence expands naturally:

ways(3) = ways(2) + ways(1) = 2 + 1 = 3 ways(4) = ways(3) + ways(2) = 3 + 2 = 5 ways(5) = ways(4) + ways(3) = 5 + 3 = 8

8. Why This Looks Like Fibonacci

The Fibonacci sequence is:

1, 1, 2, 3, 5, 8, 13, ...

where each number is the sum of the previous two.

Climbing Stairs produces:

1, 2, 3, 5, 8, 13, ...

The recurrence is the same:

ways(n) = ways(n - 1) + ways(n - 2)

The difference is simply where we choose to start the sequence. The important lesson is not "Climbing Stairs is Fibonacci." The important lesson is:

Many DP problems have a recurrence that looks familiar because the underlying structure is similar. The real skill is learning how to derive that recurrence from the problem.

9. Where Does Dynamic Programming Come In?

At this point, someone might reasonably ask:

Isn't this just recursion or the Fibonacci sequence? Why are we calling it dynamic programming?

That is a very good question.

The key point is not the equation itself. The key point is that the solution to a larger problem depends on solutions to smaller problems, and those smaller results can be reused instead of recalculated.

Imagine calculating ways(5) recursively without remembering anything. To calculate it, you need ways(4) and ways(3). But while calculating ways(4), you again need ways(3) and ways(2).

So ways(3) gets calculated multiple times.

Dynamic programming says:

"If I have already solved a smaller problem, don't solve it again. Remember the answer and reuse it."

10. The DP Perspective

We can define a very simple state:

dp[i] = number of ways to reach step i

Then the transition is:

dp[i] = dp[i - 1] + dp[i - 2]

In plain English:

"The number of ways to reach step i comes from either the previous step or the one before that."

That is a typical DP pattern: break the larger problem into smaller versions of the same problem, and store the answers as you go.

11. Brute Force vs. DP

Without DP, a recursive solution would try both choices at every step:

Take 1 step OR Take 2 steps

This creates a decision tree. As n grows, the number of branches grows exponentially.

Because many branches recompute the same small states, the naive solution wastes time.

The big idea in DP is: if we have already solved a smaller problem, we should not solve it again.

12. The First DP Version: Store the Answers

A straightforward way is to create an array dp:

int[] dp = new int[n + 1]; dp[1] = 1; if (n >= 2) dp[2] = 2; for (int i = 3; i <= n; i++) { dp[i] = dp[i - 1] + dp[i - 2]; } return dp[n];

Now the array acts like a notebook: each time we solve a smaller problem, we write the answer down and reuse it later.

13. But Do We Really Need the Whole Array?

To calculate dp[i], do we need all earlier values?

No. We only need the previous two answers.

Look again:

dp[i] = dp[i - 1] + dp[i - 2]

That means we only need the answer from the most recent step and the one before it. The older values can be discarded.

That gives us a space optimization.

We can store only the last two states instead of the entire history.

14. The Two-Variable Implementation

Here is the optimized C# solution:

using System; class Program { static int ClimbStairs(int n) { if (n <= 2) return n; int prev2 = 1; int prev1 = 2; for (int i = 3; i <= n; i++) { int current = prev1 + prev2; prev2 = prev1; prev1 = current; } return prev1; } static void Main() { int n = 4; Console.WriteLine(ClimbStairs(n)); } }

For n = 4, this prints:

5

Let's slow it down and understand exactly what happens inside the loop.

Before the loop

prev2 = 1 prev1 = 2

These represent:

ways(1) = 1 ways(2) = 2

When i = 3

current = prev1 + prev2 = 2 + 1 = 3

So:

ways(3) = 3

Then we shift the variables:

prev2 = prev1 = 2 prev1 = current = 3

When i = 4

current = prev1 + prev2 = 3 + 2 = 5

So:

ways(4) = 5

Then the variables shift again and we are ready for the next step.

16. Complexity

The loop runs from 3 through n, so it performs roughly n iterations.

Time: O(n)

Memory is constant because we only store a few integers.

Extra Space: O(1)

17. The Mental Model for DP

If you are learning DP for the first time, do not try to memorize a collection of formulas immediately. Start with this mental model:

1. I have a big problem.

2. Can I describe it using smaller versions of the same problem?

3. If I solve those smaller problems, can I combine their answers?

4. Will I need the same smaller answers again?

5. If yes, remember them instead of recalculating them.

Climbing Stairs is almost the smallest possible example of this thought process.

18. What Is the “State” Here?

DP terminology can sound intimidating, but the word state is often much simpler than it sounds.

In this problem, we can define:

dp[i] = number of ways to reach step i

That is the state.

We are simply saying:

“For each step, I want to know how many ways there are to get there.”

Then the transition is:

dp[i] = dp[i - 1] + dp[i - 2]

If you hear someone say “define the DP state,” they often mean:

"What information do I want to remember for each smaller version of the problem?"

19. The Most Important Pattern to Remember

When you see a new problem, do not immediately ask:

"What is the DP formula?"

Instead ask:

  1. What does my state represent?
  2. What is the last decision or move?
  3. Where could I have come from immediately before that?
  4. Can I divide all possible solutions into distinct cases?
  5. Can each case be expressed using a smaller problem?

For Climbing Stairs:

State: ways(n) = number of ways to reach n Last move: +1 or +2 Previous step: n - 1 or n - 2 Therefore: ways(n) = ways(n - 1) + ways(n - 2)

This is the pattern that appears again and again in DP problems.

20. Final Takeaway

The Climbing Stairs problem is such a good introduction to DP because it shows the core idea in a language that is easy to understand:

  • Break a problem into smaller versions of the same problem.
  • Ask what the last choice could have been.
  • Build the answer from smaller states.
  • Remember those smaller answers instead of recomputing them.

And once you see that pattern, the recurrence no longer looks like a magical formula. It becomes something you can derive from the structure of the problem itself.

In short: dynamic programming is not about complexity for its own sake. It is about recognizing that many problems can be solved by reusing smaller subproblems. Climbing Stairs is the cleanest possible example of that idea.
