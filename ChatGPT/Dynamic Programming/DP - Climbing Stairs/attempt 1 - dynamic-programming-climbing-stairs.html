Dynamic Programming, Explained with the Simplest Example: Climbing Stairs

Dynamic Programming (DP) is one of those topics in programming that can initially sound much more complicated than it actually is.

The name itself can make it feel mathematical or advanced. You may hear words such as state, transition, recurrence, memoization, and tabulation and wonder whether you need to understand all of that before solving your first DP problem.

You don't.

A much better way to learn DP is to start with a problem so simple that the underlying idea becomes almost impossible to miss. The classic Climbing Stairs problem is perfect for that.

In this post, we will start with the problem itself, solve it in the most natural way, notice the repeated work, and then gradually turn that observation into a dynamic programming solution. We will also look at an implementation that uses only two variables instead of a DP array.

The goal is not merely to memorize a solution. The goal is to understand why this is DP and, more importantly, how you can recognize the same pattern when a different problem appears in an interview or coding exercise.

1. The Problem: Climbing Stairs

Imagine that you are standing at the bottom of a staircase.

The staircase has n steps.

You are allowed to climb either:

  • 1 step at a time, or
  • 2 steps at a time.

The question is:

How many different ways can you reach the top?

Let's start with a very small staircase so that we can solve it by hand.

If there is only 1 step

There is only one possible way:

1

So there is 1 way to reach the top.

If there are 2 steps

There are two possibilities:

1 + 1 2

So there are 2 ways.

If there are 3 steps

Now things become slightly more interesting:

1 + 1 + 1 1 + 2 2 + 1

There are 3 ways.

If there are 4 steps

We can list all possibilities:

1 + 1 + 1 + 1 1 + 1 + 2 1 + 2 + 1 2 + 1 + 1 2 + 2

There are 5 ways.

So we already have a small sequence:

Number of steps Number of ways
11
22
33
45
58
613

Something familiar may already be visible here. This is the Fibonacci-like pattern where each value is obtained by adding the previous two values.

But rather than jumping straight to a formula, let's understand why that happens.

2. The Key Question: What Could the Last Step Have Been?

Suppose we want to reach step n.

We are allowed to move either 1 or 2 steps at a time. Therefore, the final move must have been one of only two possibilities.

Possibility 1: We came from step n - 1 by taking one step.
Possibility 2: We came from step n - 2 by taking two steps.

There is no third possibility.

So, if we know how many ways there are to reach step n - 1 and how many ways there are to reach step n - 2, we can calculate the number of ways to reach step n.

ways(n) = ways(n - 1) + ways(n - 2)

This tiny equation is the heart of the problem.

Notice what we have done. Instead of trying to list every possible sequence of jumps to reach step n, we have reduced the problem to two smaller versions of the same problem.

That is the first major idea behind dynamic programming.

Big problem: How many ways can I reach step n?

Smaller problems: How many ways can I reach step n - 1 and step n - 2?

Combine them: Add those two answers.

3. Let's See the Recurrence in Action

Suppose n = 4.

Our formula says:

ways(4) = ways(3) + ways(2)

We already know:

ways(3) = 3 ways(2) = 2

Therefore:

ways(4) = 3 + 2 = 5

Now suppose we want ways(5).

ways(5) = ways(4) + ways(3)

We know:

ways(4) = 5 ways(3) = 3

So:

ways(5) = 5 + 3 = 8

And for 6:

ways(6) = ways(5) + ways(4) = 8 + 5 = 13

We are essentially building the answer one small problem at a time.

4. Where Does Dynamic Programming Come In?

At this point, someone might reasonably ask:

"Isn't this just recursion or the Fibonacci sequence? Why are we calling it dynamic programming?"

That is a very good question.

The important part is not simply the equation:

ways(n) = ways(n - 1) + ways(n - 2)

The important part is that the solution to the bigger problem depends on solutions to smaller problems, and those smaller solutions can be remembered and reused.

That reuse is what makes this a classic DP problem.

Imagine that you calculate ways(5) recursively without remembering anything. To calculate it, you need ways(4) and ways(3). But while calculating ways(4), you again need ways(3) and ways(2).

So ways(3) gets calculated more than once.

As the value of n becomes larger, this repeated work grows rapidly.

Dynamic programming says, in very simple terms:

"If I have already solved a smaller problem, don't solve it again. Remember the answer and reuse it."

5. The First DP Version: Store the Answers

One straightforward way to implement this idea is to create an array called dp.

We can let:

dp[i] = number of ways to reach step i

Now the problem becomes very easy to express.

We know the first two values:

dp[1] = 1 dp[2] = 2

For every later step:

dp[i] = dp[i - 1] + dp[i - 2]

So for 6 steps, we would build:

dp[1] = 1 dp[2] = 2 dp[3] = 3 dp[4] = 5 dp[5] = 8 dp[6] = 13

The array is essentially our notebook. Whenever we solve a smaller problem, we write its answer down.

6. But Do We Really Need the Whole Array?

Now comes a useful observation.

To calculate dp[i], do we really need all previous values?

No.

Look at the recurrence again:

dp[i] = dp[i - 1] + dp[i - 2]

We only need the previous two answers.

Once we move from step 4 to step 5, we do not need to keep every earlier value. We only need the values corresponding to the previous two positions.

That gives us a very nice space optimization.

Instead of storing:

[1, 2, 3, 5, 8, 13, ...]

we can keep only two variables:

prev2 prev1

Here:

  • prev2 represents the answer two positions behind.
  • prev1 represents the answer one position behind.

Then we calculate:

current = prev1 + prev2

After calculating the current answer, we move the variables forward.

7. Understanding the Two-Variable Implementation

Here is the C# implementation:

using System; class Program { static int ClimbStairs(int n) { if (n <= 2) return n; int prev2 = 1; int prev1 = 2; for (int i = 3; i <= n; i++) { int current = prev1 + prev2; prev2 = prev1; prev1 = current; } return prev1; } static void Main() { int n = 4; Console.WriteLine(ClimbStairs(n)); } }

For n = 4, this prints:

5

Let's slow this down and understand exactly what happens inside the loop.

Before the loop

prev2 = 1 prev1 = 2

We are saying:

ways(1) = 1 ways(2) = 2

Now the loop starts at step 3.

When i = 3

current = prev1 + prev2 = 2 + 1 = 3

So:

ways(3) = 3

Now we shift the variables:

prev2 = prev1 = 2 prev1 = current = 3

So we now have:

prev2 = 2 prev1 = 3

These represent:

ways(2) = 2 ways(3) = 3

When i = 4

Again:

current = prev1 + prev2 = 3 + 2 = 5

Therefore:

ways(4) = 5

Then we shift again:

prev2 = 3 prev1 = 5

Finally, we return prev1, which is 5.

8. Notice Something Important: There Is No DP Array

This is a useful point for beginners.

Someone might think that dynamic programming means:

"Create an array called dp and fill it."

That is not what DP means.

An array is only one way of storing previously calculated results.

In this problem, because each new answer depends only on the previous two answers, we can throw away the older values and keep just two variables.

The underlying DP idea remains exactly the same.

We are still:

  1. Breaking the problem into smaller problems.
  2. Solving those smaller problems.
  3. Remembering the answers.
  4. Using those answers to solve the next problem.

The only difference is how much of the history we keep.

9. Why Not Just Use the Formula?

For this particular problem, you may notice that the sequence is simple enough that you could calculate the answer using a mathematical formula related to Fibonacci numbers.

But that is not the point of the exercise.

In real DP problems, there often isn't a convenient mathematical formula that you can simply plug numbers into.

The important skill is learning to recognize a structure like this:

Current answer = some combination of answers to smaller problems

Once you recognize that structure, DP becomes much less mysterious.

10. The Two Questions You Should Ask When Learning DP

When you encounter a new problem that might involve dynamic programming, don't immediately ask:

"What is the DP formula?"

Instead, start with two simpler questions.

Question 1: What is the smaller version of this problem?

For Climbing Stairs:

The big question is:

How many ways can I reach step n?

A smaller version is:

How many ways can I reach step n - 1?

And another smaller version is:

How many ways can I reach step n - 2?

Question 2: Can I build the current answer from those smaller answers?

Here the answer is yes.

ways(n) = ways(n - 1) + ways(n - 2)

Once you have those two things, most of the work is already done.

11. The Difference Between Recursion and DP

This distinction is worth understanding because beginners often encounter recursion first and then wonder what makes DP different.

Imagine that we write a recursive solution that says:

ways(n) = ways(n - 1) + ways(n - 2)

The recursive approach naturally breaks the problem into smaller problems. That is good.

But it may repeatedly solve the same smaller problem.

For example, when calculating a larger value, the calculation of ways(3) may happen from multiple branches.

DP adds the idea of remembering results.

So a useful mental comparison is:

Recursion: "I can break this problem into smaller problems."
Dynamic Programming: "I can break this problem into smaller problems, and I don't want to solve the same smaller problem repeatedly."

There are two common ways to achieve that in DP.

Memoization

Memoization usually starts from a recursive solution. Whenever you solve a problem, you store its answer so that the next time you need it, you can reuse it.

Think of this as:

"Solve it when needed, then remember it."

Tabulation

Tabulation usually starts from the smallest known answers and builds upward.

Think of this as:

"Start small, fill the table, and build toward the answer."

The two-variable C# solution is essentially a space-optimized version of that bottom-up idea.

12. Why the C# Solution Is Efficient

Let's look at the complexity.

The loop runs from 3 through n. Therefore, it performs roughly n iterations.

So the time complexity is:

Time: O(n)

What about memory?

We only keep three integer variables: prev2, prev1, and current.

The amount of memory does not grow as n grows.

Extra Space: O(1)

That is an important improvement over the array version, which would use O(n) extra space.

14. The Most Important Mental Model

If you are learning DP for the first time, don't try to memorize a collection of DP patterns immediately.

Start with this mental model:

1. I have a big problem.

2. Can I describe it using smaller versions of the same problem?

3. If I solve those smaller problems, can I combine their answers?

4. Will I need the same smaller answers again?

5. If yes, remember them instead of recalculating them.

Climbing Stairs is almost the smallest possible example of this thought process.

15. One Subtle Point: What Exactly Is the "State"?

DP terminology can sound intimidating, but the word state is often much simpler than it sounds.

In this problem, we can define:

dp[i] = number of ways to reach step i

That is our state.

We are simply saying:

"For each step, I want to know how many ways there are to get there."

Then the transition is:

dp[i] = dp[i - 1] + dp[i - 2]

In plain English:

"The ways to reach this step come from either the previous step or the step before that."

So if you hear someone say "define the DP state," don't let the terminology scare you. Often, it simply means:

"What information do I want to remember for each smaller version of the problem?"

16. Why the Base Cases Matter

There is another important DP lesson hidden inside this tiny problem: the starting values matter.

Our solution begins with:

if (n <= 2) return n;

That gives us:

ways(1) = 1 ways(2) = 2

These are the values from which the rest of the solution is built.

Without correct base cases, the recurrence has nothing reliable to build on.

This is true far beyond Climbing Stairs. In many DP problems, finding the recurrence is only half the job. You also need to carefully determine the smallest cases and initialize them correctly.

17. What Happens If n Is 0?

This is an interesting edge case.

The conventional version of the Climbing Stairs problem usually says that n is at least 1. Under that assumption, the simple base case:

if (n <= 2) return n;

is perfectly acceptable.

If you decide that your own version of the problem should support n = 0, however, you need to decide what that means.

In some DP formulations, there is exactly one way to reach the starting position: do nothing.

That leads to:

ways(0) = 1

This is why you may sometimes see a slightly different initialization in other implementations.

The important lesson is not that one version is universally correct. It is that the definition of the problem determines the base cases.

18. Common Beginner Mistakes

Mistake 1: Thinking DP Requires a Big Array

As we have seen, it doesn't. The DP array is just a convenient way to remember results. If the recurrence only needs the previous two values, you can often reduce the memory requirement.

Mistake 2: Memorizing the Fibonacci Connection

It is useful to notice that Climbing Stairs produces a Fibonacci-like sequence, but memorizing that fact does not teach you how to solve other DP problems.

The more useful thing to remember is the reasoning:

Look at the final move → identify smaller problems → combine their answers.

Mistake 3: Starting With Code

A common habit in coding interviews is to immediately start typing.

With DP, that can make things unnecessarily confusing.

First write down what the smaller problem means. Then find the relationship between the smaller and larger problem. Only after that should you translate the idea into code.

Mistake 4: Ignoring What the Variables Represent

Names such as prev1 and prev2 are short and convenient, but you should always know what they mean.

In this solution:

prev2 = ways(i - 2) prev1 = ways(i - 1) current = ways(i)

Once that is clear, the variable updates stop looking like magic.

19. How to Explain This Problem in an Interview

If you were asked this problem in an interview, you do not need to immediately jump into code.

A clean explanation could be:

Step 1: To reach step n, the final jump must come from either n - 1 or n - 2.

Step 2: Therefore, the number of ways to reach n is the number of ways to reach n - 1 plus the number of ways to reach n - 2.

Step 3: We can calculate these values from the smallest cases upward.

Step 4: Since each new answer only depends on the previous two, we don't need to store the entire DP array.

Step 5: The resulting solution takes O(n) time and O(1) extra space.

That explanation demonstrates understanding rather than simply showing that you memorized a Fibonacci implementation.

20. The Bigger Lesson Behind This Tiny Problem

Climbing Stairs is deliberately simple. You probably won't encounter many real-world problems that are literally about walking up a staircase.

But the structure appears in many other situations.

For example, imagine a problem where you have several choices at each stage, and your goal is to find the best score, cheapest cost, largest profit, or number of possible combinations.

Sometimes the best answer for the current situation depends on answers you already computed for smaller situations.

That is where DP becomes powerful.

The problem might no longer look like Climbing Stairs. The story could involve:

  • choosing items in a bag,
  • making a sequence of decisions,
  • finding the cheapest path,
  • finding the longest subsequence,
  • counting possible combinations, or
  • maximizing some value under constraints.

The surface story changes, but the underlying question can remain similar:

Can I solve the current problem using answers to smaller problems that I have already solved?

21. A Simple DP Checklist

When you see a new problem and suspect it might be DP, use this checklist:

  1. Define the smaller problem. What does the answer for position, index, amount, capacity, or stage i mean?
  2. Find the choices. What decisions can I make from the current state?
  3. Look at the previous states. Where could the current answer have come from?
  4. Write the recurrence. How can previous answers produce the current answer?
  5. Find the base cases. What are the smallest inputs for which I know the answer directly?
  6. Check repeated work. Will the same smaller problems be needed multiple times?
  7. Store and reuse. Use memoization, tabulation, or a space-optimized approach.

You don't need to use all the DP terminology immediately. If you can reason through those questions in plain English, you are already learning the important part.

22. Final Comparison: Three Ways to Think About the Same Problem

It is useful to see how the same problem can be approached at different levels.

Brute-force thinking: List every possible sequence of 1-step and 2-step moves.

This becomes inefficient because many smaller cases get solved repeatedly.

Recursive thinking: To solve n, solve n - 1 and n - 2.

This captures the structure of the problem, but a naive recursive implementation can repeat work.

Dynamic programming thinking: Solve the smaller problems once, remember their answers, and reuse them.

Because only the previous two values are needed, the final implementation can use O(1) extra space.

This progression is worth remembering.

23. The One Sentence to Remember

Dynamic programming can sound like a large and complicated topic when you first encounter it. But at its core, the idea can be surprisingly simple.

Dynamic programming is about solving smaller problems once, remembering their answers, and using those answers to solve bigger problems.

In the Climbing Stairs problem, the whole idea boils down to:

ways(n) = ways(n - 1) + ways(n - 2)

And the optimized implementation simply keeps those two previous answers:

int current = prev1 + prev2; prev2 = prev1; prev1 = current;

That's it.

No complicated data structure. No mysterious algorithm. Just a big problem being reduced to smaller problems, with the useful answers remembered along the way.

If you're beginning your journey into Dynamic Programming, Climbing Stairs is a good problem to keep coming back to. Once this idea feels natural, the next step is to try slightly richer problems where the DP state represents not just a step number, but something like an index, a capacity, a position, or a combination of multiple variables.
